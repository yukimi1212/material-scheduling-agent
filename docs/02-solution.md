# 02. 解决方案设计（Solution Design）

## 1. 整体架构（System Architecture）

本项目采用轻量级 Agent 架构，使用原生 Python 实现业务流程、工具调用和模型交互，通过本地 Ollama 模型提供动态决策能力。

系统主要由以下模块组成：

| 模块 | 文件 | 主要职责 |
|---|---|---|
| 入口模块 | `main.py` | 接收用户输入，启动 Agent 并展示执行结果 |
| Agent 模块 | `agent.py` | 管理任务执行流程、前置检查、模型决策、工具调用和用户确认 |
| LLM 模块 | `llm.py` | 与 Ollama 本地模型通信，获取模型生成的决策结果 |
| 工具模块 | `tools.py` | 提供素材读取、规则检查、时段查询和草稿保存等业务工具 |
| 存储模块 | `storage.py` | 负责排期草稿的本地 JSON 文件读写 |

整体执行过程如下：

```text
                  用户输入
                     |
                     v
                main.py
                     |
                     v
                 agent.py
                     |
             素材信息读取
                     |
                规则检查
                     |
              前置条件判断
                     |
              是否允许排期？
                /       \
              否         是
              |           |
           返回阻断      LLM 决策
                          |
                          v
                    query_slots
                          |
                          v
                      工具执行
                          |
                          v
                      观察结果
                          |
                          v
                    下一轮 LLM 决策
                          |
                 是否完成决策？
                    /       \
                  否         是
                  |           |
                继续循环    排期建议
                              |
                         用户确认？
                          /     \
                        否       是
                        |         |
                      取消     保存草稿
                                  |
                                  v
                              storage.py
```

需要说明的是，素材信息读取和规则检查属于 Agent 的 Python 前置检查，并不是由模型自主选择调用的工具。模型驱动的动态决策主要发生在时段查询和后续排期建议阶段。

## 2. 核心调用流程（Execution Flow）

### 2.1 接收用户请求

用户通过 CLI 输入排期请求，例如：

```text
请安排素材 M004 在 21:00 发布。
```

Agent 从请求中获取素材 ID、用户指定的发布时间，以及是否允许调整发布时间等信息，作为后续处理的输入。

### 2.2 前置检查

在调用模型进行排期决策之前，Agent 首先执行必要的业务检查。

**第一步：读取素材信息**

调用 `read_material()` 获取素材元数据。

如果素材不存在或必要信息缺失，则停止排期，并返回相应的错误或待补充信息。

**第二步：检查审核规则**

调用 `check_rules()` 获取素材审核结果，包括审核状态、风险等级和风险原因。

如果素材存在高风险，则直接阻断排期，不再进入后续决策流程。

这样设计可以确保模型不会绕过基本业务约束。

### 2.3 模型决策与工具调用

当前置检查通过后，Agent 调用 Ollama 模型，根据用户请求和当前业务状态决定下一步动作。

模型可以选择调用 `query_slots()` 查询已有排期及可用时段。

工具执行完成后，Agent 将工具返回结果作为观察信息传递给下一轮模型调用。

模型根据新的观察结果决定是否提出排期建议、选择替代时间或阻断任务。

### 2.4 用户确认与草稿保存

当 Agent 生成有效排期建议后，不会立即保存草稿，而是先返回待确认结果。

用户可以：

- 确认：调用草稿保存工具，将排期写入本地 JSON 文件。
- 取消：终止当前排期，不创建新草稿。

保存成功后，系统更新排期状态；保存失败时，清除对应的 pending 状态，并返回明确的失败信息。

## 3. 动态决策机制（ReAct Loop）

### 3.1 设计思路

本项目采用 ReAct（Reasoning and Acting）思路组织模型与工具之间的交互。

其核心过程是：

1. 模型根据当前请求选择动作。
2. Agent 执行对应工具。
3. 工具返回实际执行结果。
4. Agent 将结果传递给模型。
5. 模型根据观察结果决定下一步动作或结束任务。

与固定规则分支相比，这种方式允许模型结合工具实际返回的信息调整决策，而不是提前写死所有时间冲突的处理结果。

### 3.2 当前实现的决策动作

模型主要使用以下动作：

| 动作 | 含义 | 适用情况 |
|---|---|---|
| `call_tool` | 调用业务工具 | 查询可用发布时间 |
| `propose_requested` | 提出用户指定时间 | 指定时间可用 |
| `propose_alternative` | 提出替代时间 | 指定时间冲突，且允许调整 |
| `block` | 阻断排期 | 存在硬性冲突或其他阻断条件 |
| `ask_user` | 请求用户进一步确认 | 需要用户参与才能继续 |

其中，模型通过 `call_tool` 请求查询时段，Agent 执行 `query_slots()` 后，将结果传递给模型进行下一轮决策。

模型不能直接假设某个时段可用，也不能推荐工具未返回的可用时间。

### 3.3 动态决策示例

假设用户请求：

```text
请安排素材 M004 在 18:00 发布。
```

查询工具返回：

```json
{
  "occupied": ["18:00"],
  "available": ["19:00", "20:00", "21:00"]
}
```

在用户允许调整发布时间的前提下，模型可以根据观察结果提出替代时间。

执行过程：

| 步骤 | 执行内容 |
|---|---|
| Step 1 | 模型选择调用 `query_slots` |
| Step 2 | Agent 执行工具，查询时段 |
| Step 3 | 工具返回 18:00 已占用，其他时段可用 |
| Step 4 | Agent 将工具结果传递给下一轮模型 |
| Step 5 | 模型选择 `propose_alternative`，提出可用替代时间 |
| Step 6 | Agent 返回建议，并等待用户确认 |

如果用户明确要求必须在 18:00 发布，则不能擅自改为 19:00，应阻断排期并说明原因。

### 3.4 执行步数限制

为了防止模型持续调用工具或陷入循环，Agent 设置了最大执行步数 `max_steps`。

当模型决策次数达到上限，但任务仍未完成时，Agent 返回 `incomplete` 状态，明确说明任务尚未完成，而不是错误地将其标记为成功。

此外，Agent 会记录模型动作、工具调用参数、工具返回结果及最终动作，形成执行 Trace，方便后续分析和问题排查。

## 4. 工具设计（Tool Design）

项目使用本地 Python 函数作为业务工具，不依赖外部业务平台。

| 工具 | 功能 | 主要作用 |
|---|---|---|
| `read_material()` | 读取素材 | 获取素材元数据 |
| `check_rules()` | 检查审核规则 | 返回审核状态和风险信息 |
| `query_slots()` | 查询发布时段 | 获取已占用和可用时段 |
| `save_schedule_draft()` | 保存排期草稿 | 将确认后的排期写入本地存储 |

工具与 Agent 分离，使业务逻辑不必直接依赖模型。

例如，模型负责根据可用时段选择建议，而工具负责判断和返回实际时段状态。最终保存操作也由 Agent 在用户确认后触发，而不是允许模型直接执行。

## 5. 数据存储设计（Storage Design）

项目使用 JSON 文件保存排期草稿，存储模块由 `storage.py` 实现。

草稿文件保存在：

```text
data/drafts/
```

每份草稿根据素材 ID 和发布时间生成对应文件名，例如：

```text
M004_2100.json
```

采用本地文件存储主要考虑到项目规模较小，不需要引入额外数据库。

同时，草稿保存与真实内容发布相互独立。保存成功仅表示排期草稿已写入本地文件，不代表素材已经正式发布。

已有草稿也会参与后续时段查询，避免相同时间被其他素材重复占用。

## 6. 异常处理与安全约束（Error Handling and Constraints）

项目针对主要异常情况设计了相应处理方式：

| 异常情况 | 处理方式 |
|---|---|
| 素材信息缺失 | 停止排期，返回待补充信息 |
| 素材审核高风险 | 阻断排期，返回风险原因 |
| 指定时段已占用 | 根据时间调整权限决定替代建议或阻断 |
| 模型返回无效时间 | 校验模型建议，不接受不可用时间 |
| 重复提交 | 返回已有草稿，不重复创建 |
| 用户取消 | 终止排期，不保存草稿 |
| 草稿保存失败 | 清除 pending 状态，返回保存失败 |
| 超出最大执行步数 | 返回未完成状态，停止继续执行 |

此外，系统通过业务工具和 Agent 层的状态校验约束模型输出，避免模型建议绕过实际可用时段和用户的硬性要求。

## 7. 技术选型与取舍（Technical Decisions）

### 7.1 原生 Python 实现 Agent

本项目没有使用 LangChain、LangGraph 等专门的 Agent 框架，而是使用原生 Python 实现模型调用、工具执行、状态管理和 ReAct 循环。

选择原因：

- 项目规模较小，原生 Python 已能够满足需求。
- 可以更直接地理解和控制 Agent 的执行过程。
- 更容易记录每一步模型动作和工具返回结果。
- 减少额外框架依赖，降低项目部署和调试复杂度。

代价是需要自行实现工具调用、执行状态管理、异常处理和循环限制等机制。

### 7.2 使用 Ollama 本地模型

项目使用 Ollama 运行本地模型 `qwen3:1.7b`，通过 HTTP API 与模型通信。

选择本地模型的原因：

- 不需要依赖外部商业模型 API。
- 不需要在项目中配置在线模型密钥。
- 便于本地开发和测试。

但小参数量模型在复杂指令理解、结构化输出和多轮决策方面存在局限，因此项目增加了输出校验和业务约束，避免完全依赖模型判断。

### 7.3 使用本地函数模拟业务工具

由于本项目主要验证 Agent 的业务决策和工具协作能力，因此使用本地 Python 函数模拟素材读取、规则检查和时段查询等业务能力。

这样可以减少外部系统依赖，让测试环境更加稳定，也便于模拟异常情况。

其局限是：当前工具返回的数据来自本地预设业务数据，不代表已经接入真实企业内容管理系统。

### 7.4 使用 JSON 文件保存草稿

对于当前项目规模，使用 JSON 文件足以满足草稿持久化需求。

相比引入数据库，这种方式实现简单、易于检查，也方便评审人员直接查看草稿内容。

但如果未来扩展为多人同时使用的业务系统，则需要考虑数据库存储、事务处理和并发控制。

### 7.5 用户确认与自动发布分离

项目没有设计自动发布功能，而是采用“生成建议—用户确认—保存草稿”的流程。

这样可以避免模型在时间选择或内容审核出现误判时，直接执行不可逆的发布操作。

将模型决策与最终业务操作分离，也是本项目的重要安全设计。

## 8. 当前方案的局限性（Limitations）

当前实现仍存在一些局限：

1. 素材信息、审核规则和时段数据使用本地模拟数据，尚未接入真实业务系统。
2. 本地小参数量模型的决策稳定性有限，复杂场景下仍需要更多测试。
3. JSON 文件存储适合当前单机演示环境，不适合直接作为高并发生产环境的持久化方案。
4. 当前审核规则较为简单，不能替代完整的内容安全审核系统。
5. Agent 采用受约束的工具调用流程，模型并不能自由调用所有业务工具。

后续可以考虑接入真实素材管理系统、数据库和内容审核服务，并进一步增强模型输出校验、日志记录和并发处理能力。
