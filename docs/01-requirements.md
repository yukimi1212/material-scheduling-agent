# 01. 需求分析（Requirements）

## 1. 项目背景（Background）

在内容运营工作中，团队通常需要处理大量待发布素材。每份素材在发布前都需要经过基本信息检查和内容规则审核，同时还需要根据发布时间要求安排合适的发布时段。

如果完全依赖人工处理，可能出现以下问题：

- 素材信息不完整，导致审核或排期无法继续。
- 素材存在内容风险，但在排期过程中未被及时发现。
- 多份素材被安排在同一时段，产生发布时间冲突。
- 用户重复提交相同的排期请求，造成重复草稿。
- 草稿保存失败，但系统仍错误地反馈操作成功。

因此，本项目设计并实现了一个**素材审核与发布排期 Agent**。它结合大语言模型和本地工具，完成素材检查、规则审核、时段查询、排期建议以及草稿保存等任务，并在必要时请求用户确认。

## 2. 目标用户（Target Users）

本项目主要面向需要管理内容素材及发布计划的内容运营人员和内容团队。

典型使用场景包括：

- 内容运营人员需要检查某份素材是否满足发布条件。
- 内容团队需要根据指定时间安排素材发布。
- 当指定时段已被占用时，需要寻找其他可用时段。
- 当素材存在风险或信息缺失时，需要明确了解阻断原因。
- 用户希望在正式发布前检查和确认排期草稿。

## 3. 项目目标（Project Objectives）

本项目的主要目标是构建一个能够根据业务状态进行动态决策的轻量级 Agent，而不只是执行固定流程的自动化脚本。

具体目标如下：

1. **素材审核：** 读取素材信息并检查审核规则，识别高风险素材和信息不完整的素材。
2. **时段查询：** 根据用户的发布时间要求查询可用时段，识别已有排期造成的冲突。
3. **动态决策：** 根据工具返回的结果，由大语言模型选择下一步动作，例如保留指定时间、提出替代时间或阻断排期。
4. **草稿管理：** 在用户确认后保存排期草稿，并检查重复提交。
5. **异常处理：** 在工具调用失败、草稿保存失败或执行达到步数限制时，明确反馈当前状态，避免错误地报告任务成功。

## 4. 功能需求（Functional Requirements）

### 4.1 素材信息读取

系统应能够根据素材 ID 读取对应的素材信息，包括素材元数据及发布时间要求。

- 素材信息完整时，允许进入后续审核流程。
- 素材信息缺失时，应停止排期并明确指出待补充的信息。
- 不应在缺少必要信息的情况下自行猜测素材内容。

### 4.2 内容规则检查

系统应能够检查素材是否满足预设审核规则，并返回审核状态、风险等级和风险原因。

- 低风险素材可以进入后续排期流程。
- 高风险素材应阻断排期。
- 审核结果应明确反映在最终输出中。

### 4.3 发布时段查询

系统应能够查询已有排期和可用发布时段。

- 用户指定的时段未被占用时，可以保留该时段作为排期建议。
- 用户指定的时段已被占用时，应根据实际可用时段进行后续决策。
- 不允许推荐工具未返回的不可用时段。

### 4.4 动态排期决策

系统使用大语言模型，根据工具返回的观察结果决定下一步动作。

主要决策包括：

- `propose_requested`：指定时段可用，提出原定时间。
- `propose_alternative`：指定时段不可用且发布时间允许调整时，提出替代时间。
- `block`：存在高风险、硬性时间冲突或其他阻断条件时，停止排期。
- `ask_user`：需要用户补充信息或进一步确认时，请求用户参与。

模型不能仅根据用户要求直接假定时段可用，也不能在缺少工具依据时自行编造替代时间。

对于用户明确指定的硬性发布时间，系统不得擅自修改；如果该时间不可用，应阻断排期，而不是自动调整。

### 4.5 用户确认与草稿保存

系统应将排期建议与正式保存操作分开处理。

- 生成排期建议后，应向用户展示建议时间和待确认事项。
- 用户确认后，才执行草稿保存。
- 用户取消后，不应保存草稿。
- 保存成功后，应返回明确的保存状态。
- 保存失败时，应明确返回失败，并清除相应的待确认状态。

本项目只保存排期草稿，不执行真实内容发布。

### 4.6 重复提交处理

系统应检查相同素材和相同发布时间是否已经存在排期草稿。

- 已存在相同排期时，应返回已有草稿信息。
- 不应重复创建相同草稿。
- 已有草稿应继续占用对应时段，避免其他素材被安排到同一时段。

### 4.7 执行过程限制

为了避免 Agent 无限循环或持续调用工具，系统应设置最大执行步数。

- Agent 应在达到最大执行步数后停止继续执行。
- 如果任务尚未完成，应返回明确的未完成状态。
- 不应将执行中断错误地标记为排期成功。

## 5. 项目范围与约束（Scope and Constraints）

### 5.1 项目范围

本项目实现以下功能：

- 本地素材信息读取。
- 基于预设规则的素材审核。
- 已有排期和可用时段查询。
- 基于大语言模型的动态排期决策。
- 用户确认、取消及排期草稿保存。
- 重复提交检查。
- 工具调用和保存失败处理。
- Agent 执行步数限制及过程记录。

### 5.2 项目不包含的功能

为了控制项目复杂度，本项目暂不实现以下功能：

- 连接真实内容发布平台。
- 自动发布文章、图片或视频。
- 对真实素材进行复杂的图像、视频或文本内容识别。
- 对接企业级内容管理系统或外部排期数据库。
- 多用户权限管理及复杂的团队协作功能。

### 5.3 技术与业务约束

- 使用本地 Ollama 模型 `qwen3:1.7b` 提供模型决策能力。
- 使用原生 Python 实现 Agent 流程和工具调用，不依赖专门的 Agent 框架。
- 素材信息、审核规则和排期时段通过本地工具提供。
- 排期草稿保存在本地文件中。
- 对模型不可用、工具异常和保存失败等情况，需要有明确的错误处理。
- Mock 测试用于验证流程和异常处理，不代表真实大语言模型的决策效果。

## 6. 成功标准（Success Criteria）

项目通过以下场景验证是否满足业务需求：

| 测试场景 | 预期结果 |
|---|---|
| 正常排期 | 素材审核通过，指定时间可用，生成排期建议并等待用户确认 |
| 素材信息缺失 | 阻止排期，明确指出缺失信息，不保存草稿 |
| 高风险素材 | 阻断排期，返回风险等级和风险原因 |
| 时段冲突 | 识别指定时间不可用，在允许调整时提出可用替代时间并等待确认 |
| 硬性时间冲突 | 不擅自修改用户指定时间，阻断排期 |
| 重复提交 | 返回已有草稿，不重复创建 |
| 用户取消 | 取消排期，不保存草稿 |
| 保存失败 | 明确返回保存失败，清除待确认状态 |
| 最大执行步数 | 停止继续执行，并明确返回未完成状态 |

除上述业务场景外，还需要满足以下技术验收要求：

1. Agent 至少实现一轮模型决策、工具执行、结果观察和后续模型决策的动态循环。
2. 工具执行结果应传递给后续模型调用，作为下一步决策依据。
3. 设置最大执行步数或工具调用次数限制。
4. 提供至少两条真实模型动态决策路径的运行记录。
5. 提供至少三组测试案例，包含实际输入、实际输出及适用的执行记录。
6. 提供单元测试，验证主要业务逻辑和异常处理。
7. 提供 README、项目源代码、测试代码、案例记录和相关设计文档，使评审人员能够按照说明复现项目。

最终成功标准是：Agent 能够在预设业务约束下完成素材审核和排期建议，能够根据实际工具结果调整决策，并在需要用户确认或发生异常时正确停止，而不是在未经确认的情况下直接执行发布。
