# 04. AI 使用说明（AI Usage）

## 1. AI 工具使用情况（AI Tools Used）

本项目采用 AI 辅助开发的方式完成。我主要使用 ChatGPT 辅助需求分析、技术方案讨论、代码开发、问题排查和测试设计，同时使用 Ollama 本地模型为 Agent 提供运行时决策能力。

| AI 工具 | 使用方式 | 主要用途 |
|---|---|---|
| ChatGPT | 开发过程中的交互式辅助工具 | 需求拆解、技术方案讨论、代码编写与调试、测试设计和文档整理 |
| Ollama（qwen3:1.7b） | 项目运行时调用的本地模型 | 理解排期请求，根据工具返回结果进行动态决策 |

在项目开发过程中，我负责整体方案的设计与实现，并根据实际运行结果决定是否采纳 AI 提供的建议。AI 主要承担辅助分析和提高开发效率的作用，最终的技术选择、业务规则和实现结果由我负责。

## 2. 个人主导的工作（My Contributions）

### 2.1 需求分析与业务逻辑设计

项目开始阶段，我首先分析题目中的业务目标和验收要求，将整体任务拆分为素材读取、规则检查、时段查询、排期决策、用户确认和草稿保存等功能。

在此基础上，我明确了系统需要遵守的关键业务约束：

- 素材信息不完整时，不能直接进入排期流程。
- 高风险素材必须阻断排期。
- 指定发布时间需要根据实际排期情况进行检查，不能默认可用。
- 替代时间必须来自工具返回的可用时段。
- 用户明确指定的硬性发布时间不能被模型擅自修改。
- 排期建议必须经过用户确认才能保存。
- 保存草稿不等于正式发布。

这些规则构成了项目的核心业务逻辑，也决定了模型可以执行的动作范围。

### 2.2 技术选型与整体架构设计

结合项目时间和实现复杂度，我选择使用原生 Python 实现 Agent，没有引入 LangChain、LangGraph 等额外框架。

我将项目拆分为入口、Agent、LLM、业务工具和存储五个模块，分别负责用户交互、流程控制、模型通信、业务操作和数据持久化。

同时，我选择 Ollama 和本地 `qwen3:1.7b` 模型进行实际运行测试，并使用 JSON 文件保存排期草稿，以减少外部服务和数据库依赖。

这些选择主要考虑了项目的可运行性、实现成本和可验证性，而不是单纯追求使用更多技术框架。

### 2.3 Agent 执行流程与动态决策设计

我重点负责设计模型与 Python 工具之间的协作方式。

在实现过程中，我将执行流程分为两个阶段：

**第一阶段：Python 前置检查**

由 Agent 调用素材读取和规则检查工具，判断素材是否满足基本排期条件。对于信息缺失或高风险素材，直接阻断后续流程。

**第二阶段：模型驱动的决策循环**

前置检查通过后，由模型根据用户请求决定是否查询可用时段。Agent 执行工具，将实际查询结果传递给下一轮模型调用，使模型能够根据观察结果调整决策。

例如，当用户指定的 18:00 已被占用时，模型需要结合工具返回的可用时段，决定保留原时间、提出替代时间或阻断排期，而不是直接生成一个未经验证的时间。

此外，我还设计了最大执行步数限制、模型输出校验和用户确认机制，避免模型无限循环、推荐无效时间或未经确认就执行保存操作。

### 2.4 核心功能实现与代码修改

在 ChatGPT 的辅助下，我完成了部分代码编写和问题分析，但并非直接采用生成结果，而是结合现有项目结构和业务要求进行调整。

个人主要参与和负责的实现工作包括：

- 设计并实现 Agent 的任务执行流程及状态管理。
- 完成 Ollama API 调用和模型响应处理。
- 实现素材读取、审核规则检查和可用时段查询工具。
- 实现 JSON 草稿持久化及已有草稿读取。
- 增加重复提交检查，避免创建相同的排期草稿。
- 增加模型建议的时间有效性校验。
- 实现用户确认、取消和保存失败处理。
- 增加最大执行步数限制和执行 Trace 记录。

在开发过程中，我根据实际运行表现不断调整 Prompt、业务约束和代码逻辑，而不是将 AI 生成的代码直接作为最终版本。

## 3. AI 辅助开发的具体应用（AI-assisted Development）

### 3.1 方案讨论与技术问题分析

对于 Agent 的执行方式、模型与工具之间的职责划分等问题，我使用 ChatGPT 讨论不同实现方案，并根据题目要求选择更适合当前项目的设计。

例如，在 ReAct 流程设计中，重点分析了如何将工具执行结果传递给下一轮模型调用，以及如何避免模型绕过业务约束。

### 3.2 代码调试与问题定位

开发过程中，我将实际运行产生的错误信息、代码片段和测试结果提供给 ChatGPT，辅助分析问题原因。

对于返回状态不一致、工具结果未正确传递、模型输出不符合预期等问题，我会先结合实际代码定位相关模块，再决定是否需要修改实现。

这种方式帮助我更快地缩小问题范围，同时也加深了对 Python、模型 API 和 Agent 执行机制的理解。

### 3.3 测试用例与文档整理

我根据题目验收要求设计六组主要业务案例，覆盖正常排期、信息缺失、时段冲突、高风险素材、重复提交和保存失败。

ChatGPT 辅助分析边界情况、整理测试记录和编写项目文档。我再根据实际运行结果检查案例内容，确保记录中的输入、输出和测试结论与真实执行情况一致。

## 4. 人工验证与质量控制（Human Verification）

我没有仅凭 AI 生成的代码或解释判断功能是否完成，而是通过实际运行和自动化测试验证实现结果。

### 4.1 真实模型运行验证

使用本地 Ollama 模型 `qwen3:1.7b` 运行 Agent，通过 CLI 输入排期请求，检查模型是否能够根据工具返回结果调整决策。

重点观察模型动作、工具调用参数、工具返回结果和最终排期状态，并将实际运行过程整理到 `examples/` 目录。

### 4.2 单元测试验证

使用 Python `unittest` 对 Agent、业务工具和存储模块进行测试。

此前共完成 34 项单元测试，均已通过。其中 Agent 模块的 10 项测试也进行了单独运行，全部通过。

测试覆盖了正常排期、替代时间、用户取消、高风险阻断、信息缺失、无效模型建议、最大执行步数、工具观察结果传递、保存失败和时间决策一致性等逻辑。

### 4.3 业务结果检查

除了检查测试是否通过，我还对关键业务结果进行了人工核对：

- 模型建议是否符合实际可用时段。
- 硬性发布时间是否得到遵守。
- 用户确认前是否没有保存草稿。
- 用户取消后是否没有创建新草稿。
- 重复提交是否避免重复创建。
- 保存失败后是否正确清除 pending 状态。
- 未完成任务是否被明确标记，而不是错误地报告成功。

对于 Mock 测试，我也明确区分其验证范围：它主要用于检查程序逻辑和异常处理，不能代替真实模型运行测试。

## 5. AI 使用的局限性与个人反思（Limitations and Reflection）

本项目的开发过程让我认识到，AI 能够提高代码编写和问题分析的效率，但不能替代开发者对业务逻辑和系统行为的理解。

首先，AI 生成的代码可能与现有项目结构不一致，也可能遗漏业务边界，因此需要结合代码和运行结果进行检查。

其次，本地小参数量模型在结构化输出和多轮决策方面存在一定局限，需要通过 Prompt 约束、工具结果校验和执行步数限制提高可靠性。

最后，单元测试通过并不意味着真实模型在所有场景下都能作出正确决策。因此，我将真实 Ollama 运行和 Mock 测试结合起来，分别验证模型交互效果和程序逻辑。

通过本项目，我不仅实践了 Python 项目开发，也进一步理解了如何将大语言模型与确定性的业务工具结合，构建一个具备动态决策能力、执行约束和异常处理机制的 Agent。

在整个过程中，AI 是辅助开发和决策的工具，而需求分析、技术方案选择、业务规则定义、代码调整及最终结果验证仍由我主导完成。
