# 03. 测试与评估（Evaluation）

## 1. 评估目标（Evaluation Objectives）

本项目的评估重点是验证素材审核与发布排期 Agent 是否能够按照预设业务规则完成任务，并在遇到异常情况时正确处理。

主要评估以下几个方面：

1. **业务逻辑正确性：** 能否正确读取素材信息、检查审核规则并查询可用时段。
2. **动态决策能力：** 能否根据工具返回的实际结果调整后续动作，而不是始终执行固定流程。
3. **业务约束遵循：** 是否能够遵守用户指定的硬性发布时间，并在必要时等待用户确认。
4. **异常处理能力：** 能否正确处理信息缺失、时间冲突、重复提交和保存失败等情况。
5. **执行过程可追踪性：** 是否能够记录模型决策、工具调用及观察结果，便于检查执行过程。

## 2. 测试方法（Testing Methods）

项目采用两种主要测试方式。

### 2.1 真实模型运行测试

使用 Ollama 本地运行的 `qwen3:1.7b` 模型，通过 CLI 输入排期请求，观察 Agent 的实际执行过程和最终结果。

主要用于验证：

- 模型能否理解用户的排期要求。
- 模型能否根据工具返回的时段信息选择下一步动作。
- 模型能否在多轮交互中调整决策。
- 用户确认前是否仅生成排期建议，而不直接保存草稿。

真实模型测试结果记录在 `examples/` 目录下的对应案例文件中。

### 2.2 单元测试与 Mock 测试

使用 Python `unittest` 对 Agent、工具和存储模块进行测试。

通过 Mock 模拟模型返回结果、工具行为和异常情况，以验证不同业务分支是否符合预期。

这种方式能够稳定地验证程序逻辑和异常处理，但不能证明真实模型在相同场景下必然产生相同决策。

## 3. 测试场景与实际结果（Test Cases）

项目围绕主要业务需求设计了六组案例。

| 案例 | 测试场景 | 预期结果 | 实际结果 |
|---|---|---|---|
| 01 | 正常排期 | 指定时间可用，生成建议并等待确认；确认后保存草稿 | 符合预期 |
| 02 | 素材信息缺失 | 阻止排期，指出缺失信息，不保存草稿 | 符合预期 |
| 03 | 时段冲突 | 识别时间冲突，根据可用时段提出替代建议并等待确认 | 已记录案例 |
| 04 | 高风险素材 | 阻断排期，返回风险等级和风险原因 | 符合预期 |
| 05 | 重复提交 | 返回已有草稿，不重复创建 | 核心逻辑符合预期 |
| 06 | 保存失败 | 返回保存失败，清除 pending 状态 | 单元测试通过 |

### 3.1 正常排期（案例01）

用户请求安排素材 M004 在 21:00 发布。

实际运行中，Agent 首先完成素材读取和规则检查，然后由模型选择查询可用时段。

工具返回 21:00 可用后，模型选择保留用户指定时间，Agent 返回待确认状态。

用户确认后，系统成功保存草稿。

最终结果：

- 素材审核通过。
- 建议发布时间为 21:00。
- 用户确认前，草稿状态为 `not_saved`。
- 用户确认后，草稿状态变为 `saved`。
- 草稿成功写入本地文件。

对应记录：`examples/01_normal_schedule.md`。

### 3.2 素材信息缺失（案例02）

用户请求安排素材 M003 在 19:00 发布。

由于素材元数据不完整，Agent 在前置检查阶段停止排期，没有继续调用模型进行时段决策。

实际返回结果：

```json
{
  "material_id": "M003",
  "review_status": "not_checked",
  "risk_level": "unknown",
  "risk_reasons": [],
  "requested_time": null,
  "suggested_time": null,
  "schedule_status": "not_scheduled",
  "pending_items": ["metadata"],
  "draft_status": "not_saved",
  "message": "素材信息不完整，暂时不能排期。"
}
```

检查草稿列表后，没有发现新增的 M003 草稿。

对应记录：`examples/02_missing_material_info.md`。

### 3.3 时段冲突（案例03）

该案例用于验证 Agent 能否根据已有排期识别时间冲突，并在允许调整的情况下提出替代时间。

重点检查：

- 是否通过工具查询实际可用时段。
- 是否将工具返回结果传递给下一轮模型调用。
- 模型是否根据观察结果调整决策。
- 替代时间是否来自工具返回的可用时段。
- 是否在用户确认之前避免保存草稿。

对应记录：`examples/03_time_conflict.md`。

### 3.4 高风险素材（案例04）

用户请求安排素材 M002 在 19:00 发布。

实际运行结果：

```json
{
  "material_id": "M002",
  "review_status": "blocked",
  "risk_level": "high",
  "risk_reasons": [
    "素材包含未经核实的信息",
    "存在内容合规风险"
  ],
  "requested_time": "19:00",
  "suggested_time": null,
  "schedule_status": "not_scheduled",
  "pending_items": ["处理审核风险后重新提交"],
  "draft_status": "not_saved",
  "message": "发现高风险，阻断排期。"
}
```

Agent 在审核阶段识别到高风险后直接阻断排期，没有生成排期建议，也没有保存草稿。

对应记录：`examples/04_high_risk_material.md`。

### 3.5 重复提交（案例05）

对已经保存过的 M004 21:00 排期再次提交相同请求。

实际结果显示：

- Agent 识别到已有排期草稿。
- 返回 `already_exists` 状态。
- 没有重复创建草稿。
- 返回已有草稿信息。

需要说明的是，已有草稿对象中的历史 `schedule_status` 字段仍显示为 `pending_confirmation`，而外层结果已经正确返回 `already_exists`。这属于返回数据的一致性问题，不影响本次重复提交检测的核心结果，后续可以进一步统一状态字段。

对应记录：`examples/05_duplicate_submission.md`。

### 3.6 保存失败（案例06）

通过 Mock 故障注入模拟草稿保存失败，验证 Agent 的异常处理逻辑。

对应单元测试：

`test_save_failure_clears_pending`

实际测试结果为 `ok`，说明保存失败后能够清除 pending 状态。

本案例属于 Mock 单元测试，不代表真实文件系统故障或真实 Ollama CLI 运行。

对应记录：`examples/06_save_failure.md`。

## 5. 已发现的问题与处理（Issues and Limitations）

### 5.1 小参数量模型的输出稳定性

本项目使用 `qwen3:1.7b` 本地模型。小参数量模型在复杂指令理解和结构化决策方面存在一定局限。

因此，项目在 Agent 层增加了输出校验和业务约束，避免模型直接决定不可用的发布时间。

### 5.2 重复提交结果中的状态字段不一致

重复提交时，外层结果正确返回 `already_exists`，但返回的历史草稿对象中仍保留了 `pending_confirmation` 状态。

该问题不影响重复检测和防止重复创建的核心功能，但可能使调用方对历史草稿状态产生误解。

### 5.3 本地模拟数据的局限

素材、审核规则和排期时段均通过本地工具提供，尚未连接真实业务系统。

因此，当前测试主要证明 Agent 流程和工具协作逻辑可运行，不能直接代表真实企业环境下的业务效果。

### 5.4 Mock 测试与真实模型测试的边界

Mock 测试可以控制模型输出和工具异常，适合验证程序逻辑，但无法证明模型在真实运行时一定会作出相同决策。

因此，项目同时保留真实 Ollama 运行案例和单元测试，以分别验证模型交互过程和程序逻辑。

## 6. 总体评估（Overall Evaluation）

目前项目已经实现素材读取、规则检查、时段查询、模型驱动的动态决策、用户确认和草稿保存等核心功能。

六组案例覆盖了正常排期、信息缺失、时段冲突、高风险素材、重复提交和保存失败等主要业务场景。

此前报告的 34 项单元测试全部通过，Agent 模块的 10 项测试也已再次运行并通过。

整体而言，当前方案能够在预设业务约束下完成排期建议，并在需要用户确认或发生异常时正确停止。

但项目仍属于本地演示和验证版本，尚未接入真实内容管理系统，也未实现正式发布能力。后续需要通过更多真实模型运行、复杂业务数据和实际业务系统集成进一步验证其可靠性。
