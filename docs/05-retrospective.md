# 05. 项目复盘与反思（Retrospective）

## 1. 项目开发过程回顾（Development Overview）

本项目从最初的需求分析、技术方案设计，到 Agent 核心流程实现、模型接入、测试和文档整理，经历了多轮设计与调整。

开发过程中，我逐渐意识到，构建一个 Agent 并不只是让大语言模型理解用户指令并生成结果，更重要的是让模型能够结合真实工具返回的信息进行决策，同时遵守业务约束，并对执行结果进行正确管理。

最初，我更关注如何让模型完成排期任务；随着开发深入，我开始关注模型是否真正使用了工具结果、决策是否符合业务规则，以及系统在异常情况下能否保持正确状态。

这种关注点的变化也是本项目中比较重要的收获。

## 2. 开发过程中遇到的主要问题与思考（Challenges and Problem Solving）

### 2.1 问题一：如何避免 Agent 退化为固定流程脚本？

**最初的想法**

项目初期，我首先考虑的是如何将素材读取、规则检查、时段查询和草稿保存等功能串联起来。最直接的方式是使用 Python 编写固定流程：按照预设顺序调用工具，再根据不同结果进入对应分支。

这种方式比较容易实现，但我很快意识到一个问题：如果所有执行路径都提前由 Python 写死，那么即使系统接入了大语言模型，也可能只是一个普通自动化脚本，而不是具备动态决策能力的 Agent。

**进一步思考**

我开始思考：

- 如果工具返回的结果与最初预期不同，模型能否根据新信息调整下一步动作？
- 如果指定时间不可用，模型是否能够根据实际可用时段重新选择？
- 如何证明模型不是简单地按照固定顺序执行，而是真的观察了工具返回结果？
- 如果模型连续调用工具，系统是否可能陷入循环？

这些问题让我重新考虑模型和 Python 代码之间的职责划分。

**解决办法**

最终采用 ReAct 思路组织模型与工具之间的交互：

1. 模型根据用户请求选择下一步动作。
2. Agent 执行模型选择的工具。
3. 工具返回实际结果。
4. Agent 将观察结果传递给下一轮模型调用。
5. 模型根据新的信息决定下一步动作或结束任务。

同时，我通过 `max_steps` 限制最大执行步数，避免无限循环。

在实现上，我没有将所有业务操作都交给模型，而是保留 Python 前置检查和关键业务校验，让模型主要负责时段查询后的动态决策。

**个人收获**

我认识到，判断一个系统是否具有 Agent 特征，不能只看它是否接入了大语言模型，而要看模型是否能够根据执行过程中获得的新信息调整后续动作。

### 2.2 问题二：模型推荐了时间，是否就意味着时间可用？

**遇到的问题**

在设计排期功能时，我最初关注的是如何让模型根据用户指定的时间给出排期建议。

但进一步考虑后，我发现模型可能根据语言上下文生成一个看似合理的时间，却并不知道这个时间是否已经被其他素材占用。

例如，用户要求在 18:00 发布，但 18:00 已经存在排期。如果模型直接推荐 19:00，也不能仅凭模型的回答就认定 19:00 一定可用。

**进一步思考**

我提出了一个关键问题：

如果模型生成的结果与真实业务数据不一致，应该相信模型还是相信工具？

我的判断是，涉及实际业务状态的信息必须以工具返回结果为依据，不能让模型凭语言生成结果代替业务检查。

另外，我还考虑了一个边界情况：

如果用户明确要求必须在 18:00 发布，即使 19:00 可用，系统是否应该自动调整？

答案是不应该。因为可用时间并不代表用户授权系统修改发布时间。

**解决办法**

我在设计中明确区分了两类信息：

- 用户约束：用户指定的发布时间，以及是否允许调整。
- 工具事实：当前已占用时段和实际可用时段。

模型只能在工具提供的可用时间范围内提出建议，同时必须遵守用户的时间调整权限。

对于允许调整的请求，可以提出替代时间并等待确认；对于硬性时间冲突，则应阻断排期。

此外，我增加了模型建议的有效性校验，避免接受工具未返回的时间。

**个人收获**

这让我进一步理解了大语言模型与传统业务逻辑的区别：

大语言模型适合处理意图理解和动态决策，但不能替代确定性的业务状态查询和约束校验。

在 Agent 系统中，模型的灵活性和业务规则的确定性需要结合，而不是相互替代。

### 2.3 问题三：模型调用工具后，如何证明它真正利用了工具结果？

**遇到的问题**

在实现模型与工具交互时，仅仅让模型调用一次工具并获得返回结果，并不能证明整个 ReAct 流程已经实现。

例如，模型调用 `query_slots()` 后，工具返回可用时段。如果下一轮模型调用没有收到这份结果，那么后续决策仍然可能是基于原始用户请求生成的。

这种情况下，虽然代码中存在工具调用，但工具实际上没有参与后续决策。

**进一步思考**

我开始关注一个更具体的问题：

如果下一轮模型没有收到工具观察结果，那么它如何知道 18:00 已经被占用？

因此，我认为需要验证的不仅是工具有没有执行成功，还包括工具返回结果是否真正传递到了下一轮模型调用。

**解决办法**

我在 Agent 中增加了观察结果传递逻辑，并通过 `test_react_observation_passed_to_next_model_call` 对这一过程进行测试。

同时，执行 Trace 记录模型动作、工具参数、工具返回结果和最终动作，使执行过程能够被检查。

**个人收获**

我认识到，Agent 的执行过程比最终输出本身更重要。

一个最终结果看似正确的系统，不一定真正经历了合理的决策过程。通过记录和验证中间步骤，可以更准确地判断模型是否利用了工具信息。

### 2.4 问题四：重复提交时，功能正确是否就代表状态正确？

**遇到的问题**

在实现重复提交检查时，我最初关注的是能否避免重复创建草稿。

经过实际运行，我发现系统已经能够识别相同素材和相同发布时间的已有草稿，并返回 `already_exists`，没有再次创建文件。

但进一步检查返回结果时，我发现一个细节：

外层结果中的 `schedule_status` 已经是 `already_exists`，而返回的历史草稿对象中仍然保留着 `pending_confirmation`。

这说明核心重复检测功能虽然正确，但不同层级的状态字段并不完全一致。

**进一步思考**

我由此想到：

如果未来其他系统或用户直接读取返回的 `draft` 对象，而不是读取外层结果，会不会误以为该草稿仍在等待确认？

这让我意识到，不能只检查主要业务结果，还需要检查返回对象内部的数据一致性。

**当前处理**

考虑到这是一个不影响核心重复检测功能的状态字段一致性问题，在本次笔试项目中，我优先保留了已经验证通过的核心功能，没有为了修复非关键问题而大幅调整代码。

同时，将这个问题记录在评估文档中，作为后续改进事项。

**个人收获**

这次经历让我认识到，软件功能的正确性不仅体现在操作结果上，也体现在数据状态的一致性上。

即使一个功能已经通过主要测试，也仍然需要检查边界情况和返回数据的完整性。

### 2.5 问题五：单元测试通过，是否就意味着 Agent 工作正常？

**遇到的问题**

项目使用 Mock 对模型返回结果和部分工具行为进行模拟。这种方式可以稳定测试不同业务分支，但也存在局限：Mock 能够控制模型输出，因此即使测试全部通过，也不能证明真实模型一定能够作出相同决策。

我开始思考：

如果单元测试通过，但本地模型在实际运行时返回了不符合预期的动作，应该如何判断项目是否真正完成？

**解决办法**

我将验证分为两个层面：

- 真实 Ollama 运行：观察模型是否理解请求、调用工具、接收观察结果并调整决策。
- Mock 单元测试：验证程序在指定模型输出和异常条件下，能否正确执行业务逻辑。

同时，保留实际 CLI 运行记录和单元测试结果，避免将两种测试的结论混在一起。

**个人收获**

我认识到，测试结果必须结合测试方式理解。

Mock 测试证明的是程序在预设条件下的逻辑正确性；真实模型运行则用于观察模型在实际交互中的表现。两者相互补充，不能相互替代。

## 3. 其他考虑过的设计问题（Design Considerations）

除了实际遇到的问题，在开发过程中我也对一些尚未发生的情况进行了思考。这些问题帮助我明确了当前方案的边界。

### 3.1 如果用户连续提交相同请求怎么办？

如果用户因为没有看到第一次请求的反馈而连续提交相同排期，系统是否应该创建多个草稿？

我的判断是，相同素材和相同发布时间应视为同一项排期请求。因此，系统增加了已有草稿检查，避免重复创建。

### 3.2 如果用户要求的发布时间永远不可用怎么办？

如果用户指定了硬性发布时间，而该时间已经被占用，系统是否应该自动寻找其他时间？

我的判断是不能自动修改。因为这涉及用户明确提出的业务约束，系统应返回冲突原因并阻断排期，而不是为了完成任务而擅自改变要求。

### 3.3 如果模型持续调用工具怎么办？

如果模型没有及时结束，而是不断请求查询时段，系统是否可能陷入无限循环？

对此，我增加了最大执行步数限制。当执行达到上限但任务仍未完成时，返回 `incomplete`，明确说明任务没有完成。

### 3.4 如果草稿已经保存，但用户再次提交呢？

如果系统只检查当前运行过程中的状态，而不读取之前保存的草稿，那么重新启动程序后可能无法识别历史排期。

因此，我采用本地 JSON 文件保存草稿，并在后续查询时读取已有草稿，使排期信息能够跨程序运行保留。

这些设计考虑让我逐渐从单次任务执行的角度，转向考虑系统在重复操作、异常情况和多次运行下的行为。

## 4. 学习收获（Key Learnings）

通过本项目，我获得了以下几方面的经验。

### 4.1 对 Agent 工程的理解更加具体

之前对大语言模型应用的理解更多集中在 Prompt 和模型调用。本项目让我进一步理解了 Agent 的核心不仅是模型生成内容，还包括工具调用、观察结果传递、状态管理和执行约束。

我也认识到，Agent 并不意味着所有操作都必须交给模型。对于确定性的业务检查和关键操作，使用传统 Python 逻辑反而更加可靠。

### 4.2 对 AI 与传统软件工程结合有了更深入的认识

本项目让我体会到，AI 能够提供灵活的意图理解和决策能力，但实际业务系统仍然需要明确的数据结构、业务规则、异常处理和测试机制。

尤其是在时间冲突和用户确认等场景中，模型建议必须受到业务规则约束。

### 4.3 提高了 Python 工程开发能力

通过项目实践，我进一步熟悉了 Python 模块划分、函数调用、异常处理、JSON 文件读写、HTTP API 调用和 `unittest` 测试。

同时，也积累了使用本地模型、检查模型响应和排查多轮调用问题的经验。

### 4.4 更重视过程验证和边界情况

开发过程中，我逐渐从关注正常流程是否能够运行，转向主动思考：

- 如果输入不完整怎么办？
- 如果工具返回的数据与预期不同怎么办？
- 如果模型输出不合法怎么办？
- 如果保存操作失败怎么办？
- 如果用户重复提交怎么办？
- 如果任务始终无法完成怎么办？

这些问题帮助我认识到，工程实现不仅要考虑正常情况，还需要明确系统在异常情况下应该如何停止和反馈。

## 5. 后续改进方向（Next Steps）

如果继续完善本项目，我计划从以下几个方面进行改进：

### 5.1 统一状态管理

进一步统一外层执行结果和草稿对象中的状态字段，避免出现重复提交时状态不一致的问题。

### 5.2 增强模型输出可靠性

进一步完善模型结构化输出解析、无效动作处理和异常恢复机制，并测试不同输入和复杂业务约束下的决策稳定性。

### 5.3 扩展业务工具

当前素材信息、审核规则和排期时段来自本地模拟数据。后续可以考虑接入真实内容管理系统、审核服务和排期数据库，使 Agent 能够处理更加真实的业务数据。

### 5.4 改进数据存储

当前使用 JSON 文件保存草稿，适合单机演示和小规模测试。如果未来需要支持多用户和并发操作，可以进一步考虑使用关系型数据库，并增加事务处理和并发控制。

### 5.5 增强执行日志和可观测性

进一步完善 Trace 结构，记录每一步的执行状态、工具调用耗时、异常信息和最终决策结果，使系统更容易调试和评估。

### 5.6 扩展真实模型评估

增加更多真实 Ollama 运行场景，比较不同提示词、模型配置和输入条件下的决策结果，进一步评估模型在复杂业务场景中的稳定性。

## 6. 项目总结（Conclusion）

本项目最大的收获并不是完成了一个能够调用大语言模型的排期程序，而是通过实际开发，逐步理解了如何将模型的动态决策能力与传统软件工程中的确定性逻辑结合起来。

从最初考虑如何串联工具，到后来关注模型是否真正利用工具观察结果，再到进一步检查重复提交、状态一致性和异常处理，我对 Agent 工程的理解逐渐从功能实现转向系统可靠性。

这个过程也让我认识到，AI 辅助开发并不意味着将设计和编码完全交给 AI。开发者仍然需要理解业务、判断技术方案、检查生成代码，并通过实际运行和测试对结果负责。
